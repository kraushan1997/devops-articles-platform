# Articles Platform: FastAPI + MongoDB on AWS EKS

A small Articles REST API deployed to **AWS EKS** in the way a production service would be. Terraform provisions the AWS infrastructure and the cluster, Helm packages the workloads, and Argo CD deploys them from git. The design has no single point of failure, and it adds observability and secure defaults.

The whole stack was **deployed to a real AWS account (us-east-1) and validated end to end**. The CRUD test ran through the public ALB, MongoDB failover was tested under load, a Karpenter scale-out was demonstrated, and time sync was checked on every node. The evidence is in [§6](#validation-evidence-live-eks-run) and [`docs/eks-run.md`](docs/eks-run.md).

| Area | What's implemented |
|---|---|
| **Application** | FastAPI + PyMongo async client, CRUD on `/articles`, `/healthz` `/readyz` `/metrics`, unit tests |
| **Containers** | Multi-stage, non-root API image; MongoDB 8.0 image with a bundled replica-set bootstrap script. CI builds both multi-arch and pushes them to **GHCR** (ECR repositories are provisioned too) |
| **Cluster (Terraform)** | **AWS EKS 1.35** in plain `aws_*` resources: VPC across 3 AZs, managed node group, EKS Pod Identity, **Karpenter**, AWS Load Balancer Controller, EBS CSI + encrypted gp3, KMS, ECR |
| **HA / no SPOF** | API ×3+ with HPA; a **3-member MongoDB replica set** as a StatefulSet, one member per AZ; PDBs, anti-affinity and zone spread; liveness, readiness and startup probes everywhere; AWS-managed multi-AZ control plane |
| **Deployment** | Two Helm charts (`charts/articles-api`, `charts/mongodb`) deployed by **Argo CD** (app-of-apps, GitOps) |
| **Observability** | kube-prometheus-stack (Prometheus ×2, Alertmanager ×3, Grafana), ServiceMonitors, alert rules and a Grafana dashboard for the API, MongoDB exporter |
| **Security** | Restricted Pod Security Standard, NetworkPolicies (VPC CNI), non-root read-only containers, secrets generated by Terraform (never in git), KMS-encrypted Secrets, IMDSv2, SHA-pinned CI actions, SBOM/provenance and a Trivy scan |
| **NTP** | EKS AL2023 nodes sync time with the Amazon Time Sync Service, verified on every node through SSM. An Ansible `chrony` role covers self-managed hosts |

## 1. Architecture overview

```mermaid
flowchart TB
  dev([Developer]) -->|git push| gh[(GitHub repo)]
  gh -->|Actions: test, build, scan| ghcr[(GHCR images)]
  gh -->|Actions: bump image tag| gh

  subgraph TF[Terraform · state in S3]
    direction LR
    l1[Layer 1: aws/1-cluster<br/>VPC · EKS · node group · add-ons<br/>Karpenter · LB Controller · ECR] --> l2[Layer 2: aws/2-platform<br/>namespaces · secrets · gp3<br/>Karpenter NodePool · Argo CD · root app]
  end

  subgraph AWS[AWS us-east-1 · VPC across 3 AZs]
    alb[Application Load Balancer<br/>internet-facing, 3 AZs]
    subgraph EKS[EKS cluster · nodes in us-east-1a / 1b / 1c]
      argo[Argo CD] -->|sync| api & mongo & mon
      subgraph articles[namespace: articles · PSA restricted]
        api[articles-api Deployment<br/>3–20 pods · HPA · PDB]
        mongo[(MongoDB StatefulSet<br/>rs0: 3 members · PDB<br/>1 per AZ · EBS gp3)]
        api -->|w=majority| mongo
      end
      subgraph monitoring[namespace: monitoring]
        mon[Prometheus ×2 · Alertmanager ×3 · Grafana]
      end
      mon -.scrape /metrics.-> api
      mon -.scrape :9216.-> mongo
      karp[Karpenter] -.launches EC2 on demand.-> EKS
    end
    alb -->|IP targets| api
  end

  gh -->|watch gitops/| argo
  ghcr -->|pull| api & mongo
  TF --> AWS
  user([Client / curl / Postman]) --> alb
```

**Request path:** client → internet-facing **ALB** (spans all 3 AZs, created by the AWS Load Balancer Controller from the Ingress) → one of ≥3 API pods (IP targets, readiness-gated) → MongoDB replica set. Writes go to the primary with `w=majority`, so they survive the loss of any one member. Reads prefer the primary.

**Control path:** Terraform builds the AWS infrastructure and the cluster (layer 1). It then installs Argo CD plus one root `Application` (layer 2). From then on, **git is the source of truth**: Argo CD syncs `gitops/apps/aws/`, which deploys kube-prometheus-stack, MongoDB and the API. CI ships a new version by committing its image tag to `gitops/values/common/images.yaml`.

### Components

| Component | Where | Notes |
|---|---|---|
| `articles-api` | `app/`, `charts/articles-api` | FastAPI on uvicorn, port 8080, UID 10001, read-only root filesystem |
| MongoDB 8.0 replica set | `images/mongodb`, `charts/mongodb` | Keyfile auth between members; the `rs-init` sidecar bootstraps the replica set and users; `mongodb_exporter` sidecar |
| Argo CD | installed by `terraform/modules/platform` | App-of-apps, HA mode (2 replicas + redis-ha) |
| kube-prometheus-stack | `gitops/apps/aws/kube-prometheus-stack.yaml` | Discovers ServiceMonitors cluster-wide |
| AWS LB Controller, Karpenter, EBS CSI, metrics-server | `terraform/environments/aws/1-cluster` | Each controller gets its own EKS Pod Identity role |

## 3. Prerequisites

The deployment was run from **AWS CloudShell**. It already has the AWS CLI, kubectl, jq, python3 and your console credentials, so no access keys are needed. Terraform goes in `/tmp`, because the CloudShell home directory is limited to 1 GB:

```bash
TF=1.15.8
curl -sLo /tmp/tf.zip https://releases.hashicorp.com/terraform/${TF}/terraform_${TF}_linux_amd64.zip
mkdir -p /tmp/bin && unzip -o /tmp/tf.zip -d /tmp/bin && export PATH=/tmp/bin:$PATH
export TF_PLUGIN_CACHE_DIR=/tmp/tfcache && mkdir -p $TF_PLUGIN_CACHE_DIR
```

| Tool | Version | Needed for |
|---|---|---|
| Terraform | ≥ 1.10 (S3 native locking) | all infrastructure |
| AWS CLI v2 | latest | credentials, `aws eks get-token`, evidence script |
| kubectl | ≥ 1.33 | cluster access |
| jq, python3 | any | test and evidence scripts |
| Helm | ≥ 3.14 | optional: `helm template` / manual installs |
| Ansible | ≥ 2.15 | optional: NTP role for self-managed hosts |

**AWS account:** an IAM principal allowed to create VPC, EKS, IAM, KMS, SQS, EventBridge, ECR and EC2 resources, plus an **S3 bucket for Terraform state** (versioning on). Never use root access keys.

**Cost while running:** about **$0.45–0.50 per hour** with `single_nat_gateway = true`. That covers the EKS control plane ($0.10/h), 3× t3.large, 1 NAT gateway, 1 ALB and about 160 GiB of gp3. Tear it down when you're done ([§14](#14-tear-down)).

**Container images:** CI publishes `ghcr.io/kraushan1997/articles-api` and `ghcr.io/kraushan1997/mongodb` as public packages, so EKS nodes pull them without a pull secret.

## 4. Cluster setup (Terraform)

Terraform is split into **two layers**, each with its own state file in S3:

1. `aws/1-cluster`: AWS infrastructure and the EKS cluster, including the controllers that need AWS IAM (Karpenter, the LB Controller, EBS CSI).
2. `aws/2-platform`: Kubernetes objects that must exist before GitOps takes over (namespaces, secrets, StorageClass, Karpenter NodePool, Argo CD).

The split exists because the Kubernetes and Helm providers need a live cluster at plan time. The first real `terraform plan` proved the point: a `kubectl_manifest` for the Karpenter NodePool in layer 1 failed to plan because the cluster did not exist yet. Every Kubernetes object now lives in layer 2. Separate state also means the in-cluster layer can be rebuilt without touching the VPC or the cluster.

### One command

```bash
export TF_STATE_BUCKET=<your-state-bucket>
./scripts/deploy-aws.sh
```

The script writes an S3 `backend_override.tf` for each layer (git-ignored), runs `plan` and asks before each `apply`. It then points kubectl at the cluster, waits for Argo CD to report everything Healthy, waits for the ALB, and runs the CRUD test.

### Step by step (what was run)

```bash
cd terraform/environments/aws/1-cluster
cp terraform.tfvars.example terraform.tfvars      # region, name, api_allowed_cidrs, single_nat_gateway
terraform init && terraform plan -out=tfplan      # Plan: 74 to add
terraform apply tfplan                            # ~17 min
aws eks update-kubeconfig --name articles-eks --region us-east-1

cd ../2-platform
terraform init && terraform plan -out=tfplan      # Plan: 15 to add
terraform apply tfplan                            # ~4 min
kubectl -n argocd get applications -w             # all Synced/Healthy ~3 min later
```

| File | What's in it |
|---|---|

## 5. Application deployment (Helm / Argo CD)

### GitOps with Argo CD

`terraform/modules/platform` installs Argo CD and a root Application that points at `gitops/apps/aws`:

| Application | Sync wave | Source |
|---|---|---|
| `kube-prometheus-stack` | 0 | prometheus-community chart 91.5.0 + `gitops/values/{common,aws}/kube-prometheus-stack.yaml` (multi-source `$values`) |
| `mongodb` | 1 | `charts/mongodb` + `gitops/values/{common,aws}/mongodb.yaml` |
| `articles-api` | 2 | `charts/articles-api` + `gitops/values/{common,aws}/articles-api.yaml` + `common/images.yaml` |

Every app has automated sync with **prune + self-heal**, retries with backoff, and `SkipDryRunOnMissingResource`. The last one lets the first sync converge while the Prometheus CRDs are still being installed. Every app also has the `resources-finalizer`, so deleting the root app cleans up everything it created, including the ALB.

To ship a change, merge to `main`. CI builds `sha-<commit>` images and commits the tag to `gitops/values/common/images.yaml`. Argo CD then performs a zero-downtime rolling update (`maxUnavailable: 0`, readiness-gated, with ALB target health as a pod readiness gate).

```bash
# Argo CD UI (from a machine with kubectl pointed at the cluster)
kubectl -n argocd port-forward svc/argocd-server 8081:80      # http://localhost:8081, user admin
kubectl -n argocd get secret argocd-initial-admin-secret -o jsonpath='{.data.password}' | base64 -d
```

### Plain Helm (without Argo CD)

```bash
kubectl create namespace articles
helm upgrade --install mongodb charts/mongodb -n articles \
  -f gitops/values/common/mongodb.yaml -f gitops/values/aws/mongodb.yaml \
  --set auth.rootPassword=$(openssl rand -hex 16) \
  --set auth.appPassword=$(openssl rand -hex 16) \
  --set auth.metricsPassword=$(openssl rand -hex 16) \
  --set auth.keyfile=$(openssl rand -hex 128)
helm upgrade --install articles-api charts/articles-api -n articles \
  -f gitops/values/common/articles-api.yaml -f gitops/values/common/images.yaml \
  -f gitops/values/aws/articles-api.yaml
```

### How the MongoDB replica set bootstraps itself

`charts/mongodb` runs `mongod --replSet rs0 --auth --keyFile …` in each of the 3 pods (`podManagementPolicy: Parallel`). An `rs-init` sidecar ([`images/mongodb/rs-init.sh`](images/mongodb/rs-init.sh)) shares each pod's network namespace. On **pod-0 only**, and idempotently, it:

1. uses MongoDB's *localhost exception* to run `rs.initiate()` with all 3 members (addressed by stable headless-service DNS names, with `mongodb-0` given the highest priority), waits for PRIMARY, then creates the `root` user;
2. authenticates as root through the replica-set seed list, so writes reach the current primary even after a failover, and creates or updates the `articles` app user (`readWrite` on `articles`) and the `metrics` user (`clusterMonitor`) with the passwords held in the Secret.

This avoids an extra operator or Job, and it survives restarts at any stage. Rotating a password in the Secret and restarting pod-0 updates the users.

## 6. Accessing and testing the API

```bash
ALB=$(kubectl -n articles get ingress articles-api -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
./scripts/test-api.sh                  # finds the ALB itself
./scripts/test-api.sh http://$ALB      # or pass it explicitly
```

The script calls **Create → List → Read → Update → Delete**, plus a read after the delete that should return 404. It prints each request and response. To make the calls by hand:

```bash
BASE=http://$ALB
curl -s -X POST $BASE/articles -H 'Content-Type: application/json' \
     -d '{"title":"Hello","content":"World","author":"me","tags":["k8s"]}'     # 201 → {"id": "..."}
curl -s $BASE/articles                                                          # 200 list (?skip=&limit=)
curl -s $BASE/articles/<id>                                                     # 200 / 404
curl -s -X PUT $BASE/articles/<id> -H 'Content-Type: application/json' -d '{"title":"Updated"}'  # 200 (partial update)
curl -s -X DELETE $BASE/articles/<id> -o /dev/null -w '%{http_code}\n'          # 204
```

| Endpoint | Behaviour |
|---|---|
| `POST /articles` | validates `title`, `content`, `author` (required) and `tags`; returns 201 with `id`, `created_at`, `updated_at` |
| `GET /articles` | newest first; `skip` ≥ 0 and `limit` 1–500 (default 50) |
| `GET /articles/{id}` | 404 for unknown or malformed ids |
| `PUT /articles/{id}` | updates only the fields sent; 400 if the body is empty |
| `DELETE /articles/{id}` | 204, or 404 |
| `/healthz`, `/readyz`, `/metrics` | liveness (process only), readiness (Mongo ping), Prometheus metrics |

## 7. Eliminating single points of failure

| Layer | SPOF removed by |
|---|---|
| Control plane | EKS: AWS-managed control plane across 3 AZs (API servers + etcd) |
| Worker nodes | 3 managed nodes, one per AZ; Karpenter adds capacity in any of the 3 AZs and replaces failed or interrupted nodes (SQS spot-interruption queue) |
| Load balancer | ALB across the 3 public subnets; the LB Controller runs 2 replicas + PDB |
| API pods | `replicaCount: 3`, HPA 3→20. **PDB** `maxUnavailable: 1`. **Pod anti-affinity** (preferred, by hostname) and **topologySpreadConstraints** (zone + hostname), so one API pod per AZ was observed |
| Rollouts | `maxSurge: 1, maxUnavailable: 0`, startup + readiness probes, `preStop` sleep so endpoints drain before SIGTERM, ALB **pod readiness gates** |
| MongoDB | **StatefulSet, 3-member replica set** (automatic failover, tested: [§6](#validation-evidence-live-eks-run)). **Required anti-affinity**, so never two members on one node. Zone spread `DoNotSchedule`, so one member per AZ. **PDB `minAvailable: 2`** keeps a voting majority through drains. `w=majority` writes + `retryWrites`. One EBS volume per member, in its AZ |
| Probes | API: liveness `/healthz` (process only, so a DB outage doesn't cause a restart storm), readiness `/readyz` (Mongo ping), startup. MongoDB: TCP liveness, `mongosh ping` readiness, generous startup probe. Exporter: HTTP probes |
| Egress | One NAT gateway per AZ by default (`single_nat_gateway = true` was used for the demo to save cost; it is the one deliberate SPOF, see What's Pending) |
| GitOps / tooling | Argo CD HA mode (2 replicas of server, repo-server and appset, plus redis-ha); Karpenter ×2 on the system nodes |
| Monitoring | Prometheus ×2, Alertmanager ×3 (gossip cluster) |

## 8. Observability

- **Metrics:** kube-prometheus-stack collects cluster metrics (node-exporter, kube-state-metrics, kubelet/cAdvisor). The API exposes RED metrics (`http_requests_total`, `http_request_duration_seconds`) through `prometheus-fastapi-instrumentator`. A `mongodb_exporter` sidecar reports each MongoDB member (replica-set state, lag, ops, connections). ServiceMonitors are part of the charts, and Prometheus selects them cluster-wide. On EKS, `up{namespace="articles"}` = 1 for all 6 targets ([evidence](docs/evidence/eks-cluster-state.txt)).
- **Dashboards:** the chart ships an *Articles API* Grafana dashboard as a labelled ConfigMap, which the Grafana sidecar loads automatically: request rate per route, 5xx ratio, p50/p95/p99 latency, ready pods, CPU and memory. The default kube-prometheus-stack dashboards cover the cluster.
- **Alerts (PrometheusRule):** API 5xx > 5%, p95 > 500 ms, fewer than 2 available replicas; `MongoDBDown`, unhealthy replica-set member, replication lag > 30 s. The stock Kubernetes and node alerts come on top of these.
- **Logs:** the API writes structured JSON logs to stdout; EKS control-plane logs (API, audit, authenticator) go to CloudWatch.
- **Access:**
  ```bash
  kubectl -n monitoring port-forward svc/kube-prometheus-stack-grafana 3000:80   # http://localhost:3000
  terraform -chdir=terraform/environments/aws/2-platform output -raw grafana_admin_password   # user: admin
  ```

## 9. Security

- **Workload hardening:** the `articles` namespace enforces the **restricted** Pod Security Standard. Every container runs as non-root with a fixed UID, drops ALL capabilities, disallows privilege escalation and uses `seccompProfile: RuntimeDefault`. The API also has a read-only root filesystem, and service-account tokens aren't mounted.
- **Network:** NetworkPolicies allow MongoDB on :27017 only from other members and the API pods, and the exporter on :9216 only from the `monitoring` namespace. The API accepts only :8080, and its egress is limited to DNS and MongoDB. The VPC CNI network-policy agent enforces them. Nodes sit in private subnets with no SSH port; access is through SSM Session Manager.
- **Secrets:** Terraform generates the MongoDB root/app/metrics passwords, the replica-set keyfile and the Grafana admin password with `random_password`, then writes them straight into Kubernetes Secrets, so nothing is committed to git. Kubernetes Secrets are envelope-encrypted with a customer-managed **KMS** key. Terraform state (which contains them) is in an encrypted S3 bucket. MongoDB uses SCRAM auth, an internal keyfile, and least-privilege users (the app user only has `readWrite` on its own database).
- **AWS:** an EKS Pod Identity role per controller (no node-wide credentials), IMDSv2 with hop limit 1, encrypted EBS (nodes and PVCs) and ECR, a CIDR-restricted API endpoint (`api_allowed_cidrs`), control-plane audit logs, and no credentials in code. Deployment ran from CloudShell with the console session's short-lived credentials.
- **Supply chain:** multi-stage minimal images, CI actions pinned by commit SHA, SBOM and provenance attestations, a Trivy scan, and immutable `sha-` tags for deployments (ECR repos use immutable tags too).

## 10. Scalability

- **Pods:** the HPA scales on CPU (70%) and memory (80%), 3→20 replicas, with a 5-minute scale-down stabilisation window. The API is stateless, so it scales horizontally.
- **Nodes:** **Karpenter** provisions right-sized spot or on-demand nodes in seconds when pods are pending, and consolidates under-used ones (`WhenEmptyOrUnderutilized`). This was demonstrated on the live cluster: a c6a.4xlarge came up in 34 s and was removed again after the load was gone. The static `system` node group is capped at 3–6.
- **Database:** WiredTiger cache and resources are sized for EKS (1–2 GiB, 0.5 GiB cache), and volumes are expandable (`allowVolumeExpansion`). Reads can be moved to secondaries by changing `readPreference`. Scaling writes further would need sharding (out of scope).

## 11. NTP on worker nodes

Kubernetes, TLS, token expiry and MongoDB elections all depend on accurate clocks.

- **EKS nodes (verified):** both the managed node group and Karpenter (`al2023@latest`) use the EKS-optimised AL2023 AMI, which ships `chrony` pointed at the **Amazon Time Sync Service** (`169.254.169.123`, link-local, available in every AZ). `scripts/collect-evidence.sh` checks this on every node through **SSM Run Command** (`chronyc tracking`). All 3 nodes reported reference `169.254.169.123`, leap status Normal, and offsets of 1–8 µs ([evidence](docs/evidence/eks-cluster-state.txt)).
- **Self-managed hosts:** `ansible/` provides a `chrony` role for hosts that don't come with this setup (custom-AMI EC2 workers, bastions, CI runners). It removes competing daemons (ntpd, systemd-timesyncd), installs chrony and other node dependencies (conntrack, socat, ethtool, NFS client), and templates `chrony.conf` (Amazon Time Sync when on AWS, `pool.ntp.org` otherwise, `makestep`, `rtcsync`). It then forces a sync and **asserts the clock offset is under 0.5 s**.

```bash
cd ansible
cp inventories/hosts.ini.example inventories/hosts.ini   # list the hosts
ansible-playbook site.yml --check && ansible-playbook site.yml
```

## 13. Design decisions

| Decision | Why | Trade-off / alternative |
|---|---|---|
| **EKS** | Managed multi-AZ control plane, native ALB/EBS/IAM integration | Control-plane cost ($0.10/h); more AWS resources than a single-VM cluster |
| **Plain `aws_*` resources (no community modules)** | Every VPC, IAM and EKS object is visible and reviewable in one place; nothing is hidden behind module defaults | More lines of code; module upgrades don't come for free |
| **Two Terraform layers** | The Kubernetes/Helm providers need a live cluster at plan time (confirmed by the first real plan); separate state gives a smaller blast radius | Two `apply`s (wrapped in `deploy-aws.sh`) |
| **Terraform does bootstrap, Argo CD does the rest** | Terraform is good at infrastructure and one-time bootstrap; Argo CD handles drift correction, self-healing and auditability for workloads | Two tools to learn |
| **Managed node group + Karpenter** | Karpenter can't schedule itself, so a small static system pool is needed; everything else scales just-in-time on spot | Slightly more moving parts than node groups + Cluster Autoscaler |
| **EKS Pod Identity instead of IRSA** | One trust principal (`pods.eks.amazonaws.com`) for every role, with no per-role OIDC conditions | Needs the pod-identity-agent add-on; not supported on Fargate |
| **No Fargate profile** | DaemonSets (VPC CNI, node-exporter, EBS CSI node) and EBS volumes (MongoDB) don't work on Fargate, and Pod Identity doesn't either | Karpenter and the managed node group cover the "no nodes to manage" goal |
| **ALB with IP targets** | Traffic goes straight to pod IPs across all AZs; pod readiness gates make rollouts wait for ALB health checks | One ALB per Ingress group (fine here) |
| **Own MongoDB chart** (not Bitnami or an operator) | Bitnami moved its images behind a paywall in 2025, and operators add CRDs and a controller to run. A small chart shows every HA mechanism explicitly (StatefulSet, keyfile, PDB, anti-affinity, bootstrap) | Day-2 automation (backups, resizing the replica set, version upgrades) is manual. An operator (MongoDB Community, Percona) or Amazon DocumentDB/Atlas would cover it in production |
| **rs-init sidecar with the localhost exception** | Bootstraps with no bootstrap credentials outside the pod, no Job ordering or hooks (which Argo CD handles differently), and is idempotent | Adds a small idle container per pod |
| **gp3 `Retain` + `WaitForFirstConsumer`** | Volumes are created in the AZ where the pod lands; data survives an accidental PVC or StatefulSet deletion | Retained volumes must be deleted explicitly on teardown (`destroy-aws.sh` does it) |
| **Secrets from Terraform `random_password`** | Nothing sensitive in git, no extra controller | Secrets live in Terraform state, which must be encrypted. External Secrets Operator + AWS Secrets Manager would be the next step |
| **GHCR** | Built into GitHub Actions (`GITHUB_TOKEN`); public images need no pull secret on EKS | ECR is also provisioned for an AWS-only registry |
| **FastAPI + PyMongo async** | Small, typed, validated request models; the native async driver replaces Motor, which is deprecated upstream | Go would give a smaller image and lower memory use |
| **Hard anti-affinity for MongoDB, soft for the API** | Losing one node or AZ must never take out a Mongo majority. The API should still be able to scale beyond the node count | MongoDB needs ≥ 3 schedulable nodes |
| **Liveness doesn't check the DB** | Avoids restarting every API pod during a Mongo failover; readiness removes them from traffic instead | — |

## 14. Tear down

```bash
export TF_STATE_BUCKET=<your-state-bucket>
./scripts/destroy-aws.sh
```

The order matters, so nothing keeps billing and `terraform destroy` doesn't hang:

1. Delete the Argo CD root app. It cascades through the finalizers: the Ingress goes, so the LB Controller deletes the **ALB**.
2. Delete the Karpenter NodePool and NodeClaims, so Karpenter terminates its EC2 instances.
3. `terraform destroy` layer 2, then layer 1 (VPC, NAT, EKS, IAM, KMS key scheduled for deletion).
4. Delete the EBS volumes kept by the `Retain` policy (MongoDB and Prometheus data).
5. Check for leftover load balancers and instances.

## What's Pending

These are either not done yet or what I'd add next for production.

1. **TLS and DNS:** ExternalDNS (Route 53) with a Pod Identity role, and an ACM certificate on the ALB. The `certificate-arn` + `ssl-redirect` annotations are already stubbed in `gitops/values/aws/articles-api.yaml`. Today the API is served over plain HTTP on the ALB hostname.
2. **NAT per AZ:** the demo ran with `single_nat_gateway = true` to save cost, so egress from two AZs depends on one NAT. Production uses the default (`false`), which gives one NAT per AZ.
3. **Restrict the EKS API endpoint:** the demo used `api_allowed_cidrs = ["0.0.0.0/0"]` because CloudShell egress IPs vary. Production should use the office/VPN CIDR, or a private-only endpoint with a bastion or SSM.
4. **Secret management:** External Secrets Operator reading from AWS Secrets Manager, so passwords never sit in Terraform state. Plus rotation.
5. **MongoDB day-2:** scheduled backups (Percona Backup for MongoDB to S3, or AWS Backup / Velero with EBS snapshots), a tested restore, and TLS between clients and members. A move to an operator or a managed service is worth considering.
6. **Logs and traces:** centralised logs (Loki + Grafana Alloy, or CloudWatch Container Insights / Fluent Bit), and OpenTelemetry + Tempo/X-Ray for traces. Alertmanager receivers (Slack/PagerDuty) need to be configured.
7. **Grafana/Argo CD exposure:** both are reachable only by `kubectl port-forward` today. Next step: an internal ALB with SSO (Cognito/OIDC).
8. **Policy and supply chain:** Kyverno or Gatekeeper policies (signed images with cosign, required probes and limits), and making the Trivy gate fail the build on fixable CRITICAL findings.
9. **Delivery:** separate dev/stage/prod environments (`gitops/apps/<env>`, `gitops/values/<env>`) with promotion, Argo CD SSO and a restricted `AppProject`, and Argo Rollouts canaries driven by the Prometheus SLOs above.
10. **Load testing:** k6 tests to tune HPA targets, resource requests and the Karpenter NodePool limits.
